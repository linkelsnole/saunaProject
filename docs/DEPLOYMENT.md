# Обновление малой сауны

## Как пользоваться после первоначальной настройки

1. Сохранить изменения в Git и отправить на GitHub. На push и pull request запускаются тесты фронта, backend и загрузчика; затем собирается JAR.
2. После попадания в `main` успешная сборка автоматически публикуется. Сервер самостоятельно скачает и проверит JAR. VPN для этого не требуется.
3. При `automatic: true` загрузчик самостоятельно устанавливает проверенную версию. Действия пользователя не нужны.
4. Открытая страница останется на экране во время перезапуска. После подтверждённой установки она перезагрузится сама. При открытии сайта с нуля во время перезапуска сервер временно недоступен.

Публикация в GitHub запускает доставку через внешний загрузчик. Все роли видят экран ожидания и автоматически получают новую страницу. Управление восстановлением версий остаётся доступным только администратору.

Вкладка «Обновление» в настройках управляет обновлением контроллера и не относится к обновлению веб-панели.

## Проверки перед установкой

- CI проверяет React/TypeScript, Java 8, Python-загрузчик, содержимое JAR и отсутствие файлов БД/токенов в Git.
- Production-релиз выпускается только из main после успешных проверок. Push в main публикует production-кандидат; ветка codex/sauna-updater публикует только lab. Run workflow из main позволяет выбрать lab отдельно.
- Загрузчик проверяет репозиторий, workflow, commit, успешное завершение запуска CI, размер и SHA-256 JAR.
- Перед установкой JAR запускается отдельно с временной базой и `127.0.0.1:1` вместо реального сервера данных. Проверяется старт Java, HTML и создание таблицы пользователей.
- Перед заменой сохраняются старый JAR и SQLite. Команды управления только `sudo service webpanel-s stop/start`.
- При ошибке старые JAR и БД возвращаются, затем проверяется запуск. Неудачная версия не устанавливается каждую минуту повторно.
- После аварийного прерывания самого загрузчика автоматические установки блокируются. Нужно проверить `attempt.json`, службу и резервные копии. Самопроизвольное восстановление после отключения питания не обещается.

Проверка запуска не заменяет испытание оборудования. Загрузчик не отправляет команды реальному PLC.

## Первоначальная настройка

Сначала выполняется испытание в отдельном `/opt/webpanel/sauna-updater-lab`, не связанном с работающими службами:

```bash
python3 tools/deployment/setup.py --install-lab
```

Push в `codex/sauna-updater` запускает проверки и публикацию lab-релиза. Сервер сначала проверяет JAR с временной базой, затем запускает отдельную постоянную тестовую панель; следующие версии ждут кнопку администратора. Результат хранится в `status.json`. Токен уже хранится отдельно в `/opt/webpanel/.config/sauna-updater-small/github.token`, права 0600. Не копировать токен в GitHub Actions или репозиторий.

После успешного испытания нужна **одна первоначальная установка** версии с новым окном через существующий `deploy-small.py`. Старая версия приложения не умеет показывать новую кнопку. Не считать production готовым до такой установки и настройки внешнего загрузчика.

Production-загрузчик должен находиться в `/opt/webpanel/.local/state/sauna-updater-small` (совпадает с домашним каталогом пользователя службы). Его `config.json` содержит:

```json
{
  "target": "production",
  "enabled": true,
  "automatic": true,
  "service": "webpanel-s",
  "root": "/opt/webpanel/.local/state/sauna-updater-small",
  "token": "/opt/webpanel/.config/sauna-updater-small/github.token",
  "jar": "/opt/webpanel/sauna-release-20260915-2317/small/sauna.jar",
  "database": "/opt/webpanel/sauna-release-20260915-2317/small/sauna_app.db",
  "port": 8082
}
```

Перед включением сверить путь БД и JAR с `systemctl show webpanel-s`. `systemctl` используется только для чтения. Добавить загрузчик в crontab пользователя webpanel раз в минуту и создать файл `ui-enabled` в его каталоге только после успешной проверки. API не читает токен и не принимает команды/пути от браузера.

В каталоге загрузчика фиксированное число рабочих файлов: `candidate.jar`, `candidate.json`, `request.json`, `status.json`, `attempt.json`, `smoke.log`, `updater.lock`, код и конфигурация. Временные базы удаляются после проверки. Резервные копии рабочих JAR/БД сохраняются рядом с приложением; удалять вручную после подтверждения версии, не удалять автоматически последнюю рабочую копию.

## Где что лежит в репозитории

- `tools/deployment/` — CI, получение релиза, проверка и настройка загрузчика.
- `tools/deploy_small_remote.py` — установка и откат `webpanel-s`; используется и ручным SSH-деплоем.
- `deploy-small.py` — резервный ручной деплой малой сауны.
- `deploy-301.py` и `tools/deploy_301.sh` — отдельная установка в 301.
- `tools/legacy/` — старые скрипты, не использовать для новых служб.
- `docs/` — инструкции по функциям и деплою.

`bars`, `bars-s`, `webpanel`, `webpanel2`, `webpanel-b` этот загрузчик не изменяет. Большая сауна требует отдельного подключения и испытания.

## CI и изменения тестов

Тесты должны исправляться при изменении требований или доказанной ошибке теста. Не ослаблять проверки, чтобы CI стал зелёным. CODEOWNERS назначает владельца на тесты и deployment; требование review действует только вместе с соответствующей защитой main на GitHub. Наличие CI само по себе не запрещает менять тесты.

GitHub Run workflow появляется после попадания workflow в основную ветку. Инструкция GitHub: https://docs.github.com/actions/managing-workflow-runs/manually-running-a-workflow

## Испытание без объединения в main

Ветка `codex/sauna-updater` публикует только `small-lab-*` после успешного CI. Production-получатель такую версию не принимает. Основная ветка и работающие сервисы при этом не меняются.

В `/opt/webpanel/sauna-updater-lab/instance` работает отдельная панель на `127.0.0.1:18082`, со своей SQLite и отключённым доступом к PLC. Первый прошедший проверку JAR запускается автоматически; следующие ждут кнопку администратора. Загрузчик раз в минуту проверяет релизы и восстанавливает тестовый процесс после перезапуска сервера.

Для просмотра через существующий SSH-доступ:

```bash
ssh -i ~/.ssh/deploy_key -o ExitOnForwardFailure=yes -N -L 127.0.0.1:18082:127.0.0.1:18082 webpanel@212.164.86.237
```

Открыть `http://127.0.0.1:18082`. Для этого диагностического туннеля нужен разрешённый маршрут к SSH; само скачивание JAR с GitHub выполняет сервер без участия Mac.

### Прямой адрес тестовой панели

`python3 tools/deployment/setup.py --install-lab --public-lab` настраивает тестовую панель на `0.0.0.0:8087`. При смене адреса уже запущенный тестовый процесс нужно перезапустить. Публичный адрес: `http://212.164.86.237:8087`. Порты рабочих панелей 8082/8083 не меняются; база отдельная, доступ к PLC отключён. Последующие запуски настройки для этого варианта выполнять с `--public-lab`.

## История трёх версий панели

Администратор открывает «Версии панели» в меню профиля. Это отдельная функция от вкладки обновления контроллера. `history.json` и каталог `versions/` сохраняют текущую и две предыдущие версии с описанием из commit subject. Старые резервные копии вне этого каталога автоматически не удаляются.

Восстановление требует подтверждения: возвращаются **JAR и снимок SQLite**, включая пользователей и настройки панели на дату снимка. Сначала проверяются SHA-256 обоих файлов, целостность JAR и SQLite. Восстановление доступно без GitHub. После отката загрузчик не устанавливает ту же новую версию повторно автоматически; более новая публикация или явный запрос администратора снимают это ограничение.

До замены JAR загрузка проходит проверку размера, SHA-256 и пробный запуск. При неудачном запуске службы установщик возвращает предыдущие JAR и БД. Отключение браузера или Mac не останавливает внешний загрузчик на сервере. Потеря питания сервера или принудительное завершение установщика посреди операции требуют проверки незавершённой установки; автоматическое восстановление после таких событий не гарантируется.

По умолчанию установка требует кнопки администратора. Только явное `"automatic": true` в конфигурации разрешает установку прошедших CI production-релизов без подтверждения. Проверка GitHub выполняется раз в минуту; опрос состояния браузером не увеличивает частоту запросов к GitHub.


## Автоматический переход открытой страницы

Каждая сборка получает уникальный `buildId`, одинаковый в JavaScript и `static/panel-build.json` внутри JAR. Публичный GET `/api/v1/platform-state` сообщает только ID запущенной сборки и признак установки, с `Cache-Control: no-store`.

Браузер проверяет состояние каждые 5 секунд, при возвращении на вкладку и взаимодействии. Во время установки показывает загрузку и проверяет каждые 2 секунды. После завершения перезагружает страницу; если установка откатилась, также возвращается к работающей версии. Сбой сети сам по себе не объявляется обновлением. Старая вкладка после сна сравнивает ID своей сборки с сервером.

Запросы интерфейса передают `X-Panel-Build`. Сервер отклоняет изменяющие запросы устаревшего интерфейса и запросы во время установки до вызова обработчика. Клиент не повторяет такие команды после перезагрузки. Уже принятые сервером команды это не отменяет. Несохранённый ввод при перезагрузке не переносится.

Для уже установленного загрузчика включить режим на сервере от его пользователя:

```bash
python3 tools/deployment/set_automatic.py --config /absolute/path/to/sauna-updater-APP/config.json
```

Скрипт проверяет существующую конфигурацию, берёт блокировку загрузчика и атомарно добавляет `automatic: true`. Он не создаёт новую службу и не запускает установку сам: её выполнит существующее минутное задание. До включения нужна первоначальная установка JAR с новым интерфейсом. Старая открытая вкладка ещё не содержит нового механизма — её один раз нужно перезагрузить.
